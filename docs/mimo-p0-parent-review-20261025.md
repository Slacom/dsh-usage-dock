## 3. 认证通信：采用已提供的owner通道

已独立核对当前`dsh-client-connection`：

- `admit`验证Host/Origin围栏、签名浏览器凭据或有效API Peer；不是单靠localhost。
- `connection.fetch.register`匹配具体路由后还检查`peer.principal.kind === 'owner'`，这是应复用的授权闸门。
- `requestRejection`只封装`admit`，**单独调用不能替代上述owner角色检查**。不采用“只加requestRejection就等同owner保护”的降级。
- 所有MiMo认证资源（状态GET、二维码资源、开始/取消/注销）一视同仁走owner闸门、`no-store`、严格方法/JSON及资源大小限制；未授权请求在读取/改变会话之前拒绝。
- `connection`采用可选服务读取；能力缺失则该认证功能关闭并说明原因，旧手工余额与其它渠道不受影响。不能把必选inject扩大成缺服务时整插件不启动。

本插件旧exact只读路由优先于SDK的`/api`前缀路由的情况已确认；本期先保证新高敏认证通道不照搬旧模式，不未经授权重构其它路由。

## 4. 存储：证明范围与待选方案

当前`credentials-local`实现明文refs/records YAML、原子写及锁；POSIX权限检查不等于Windows ACL或DPAPI。公开随包能力名称清单里有credentials与credentials-local，未看到另一个显名的加密provider；Desktop入口未暴露safeStorage调用。**此范围不足以证明所有宿主/自定义provider都无安全封装**。

record可以仅作为密文载体，但加密密钥不能与密文一同明文放在record/config。可继续评估Windows CurrentUser DPAPI封装；若使用外部进程，必须固定可信程序与代码，秘密只走受控内存通道、不进参数/日志/临时明文文件，受预算/取消和输出上限约束。Android无此能力时不可要求安装PowerShell；能力差异必须显式显示并另行验收。

中央`DSH_HOME`记录库的键格式是命名规则，不是安全ACL。PoC/生产记录都必须设计profile与插件实例的稳定隔离，不能所有实例共用固定`usage-dock/mimo-account`。注销只清所属记录；替换账号与迟到写回需要同一代次守卫。

## 5. 对实施方案的裁定

- SDK与运行时探针只处理公开源码或合成Cookie/随机数据；结果必须标执行模式，不能把OS API可用、另一Node可用宣传为Host适配已完成。
- 临时回环HTTP fixture用于离线测试后自行关闭，不是替换现有GUI的新服务器。真实PoC如需独立本机页面/进程，须在账户测试授权时明确说明，不暗中安装或替换当前插件。
- P1代码可在`tools/poc/mimo-auth/`隔离，不进入npm包；只有父批准具体安全方案后才开始。真实扫码/余额/跨重启/续期仍需用户具体同意，二维码和能力URL仅在本机授权UI短时显示。
- 短期服务票轮换不等于切账号；利用现有`beginOp/isCurrentOp/recordSampledCredential`语义，区分逻辑账号代次与实际发送凭据的冻结快照，不让合法续期撤销自己的结果，也不让旧会话余额在注销后复活。
- 单消费者取消只终止自己的等待，不能把其signal并入共享请求根；生命周期/注销等再撤销所属共享工作。
- 账号/平台Cookie按每跳来源收、目标域发，必要的受信跨域SSO只能走**预先批准**的精确白名单；未知跳转立即停，不“先跟随再学习”。
