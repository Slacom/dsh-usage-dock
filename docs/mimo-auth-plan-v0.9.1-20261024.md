## 1. 主线与不做项

“长期额度显示”按交接理解为：**在服务器认可账号会话的前提下，减少反复手填Cookie，让真实MiMo钱包余额持续可读**，不是增加一个长期/月度Token额度池。

主链：官方二维码 → 用户确认 → 最小必要账号会话 → api-platform平台会话 → `/api/v1/balance` → 原有余额、现金、赠送、币种与阈值。

不承诺永久登录：长期账号票被撤销或遇MFA/CAPTCHA/风控时，诚实要求重新扫码，不绕过验证。

明确不做：浏览器/CDP/Playwright登录助手、浏览器或其他插件认证文件读取、Token Plan套餐监控、MiMo模型调用代理、充值、跨设备令牌同步、全渠道缓存改造、其它UI重排或来源/计费池自动认证。保留旧`mimoCookie`手动模式，不自动迁移、删除或覆盖已有值。

## 3. 两个必须先通过的安全闸门

### 3.1 可验证的Host秘密存储

先核实当前宿主的公开服务、隔离、写入/删除与加密能力。现有代码证明使用了`credentials.resolve`，**不证明**有可写的加密凭据库。

`role('secret')`隐藏表单投影不等于落盘加密；文件存在、目录私有或`chmod 0600`也不能代替Windows DPAPI/Android Keystore的证明。原规划先核安全能力、不静默用明文JSON降级。**用户于2026-10-25 20:24在获告长期票明文、Windows未校验ACL及会话滥用风险后，明确选择「使用宿主现有未加密凭据库」。** 本次按这一知情选择开发：使用正式Host records接口并做profile/实例归属与代次校验，不改为本地JSON/配置存票，不声称加密，不继续扩DPAPI/Keystore分支；这不是已授权现在发起真实扫码。Desktop/Android服务是否存在仍逐宿主验证，缺服务时不能静默降级到其它秘密文件。

只保存已证明必要的最小账号状态与平台票，不保存二维码、轮询票据、一次性URL或响应全文；每个profile/插件实例隔离，原子写、损坏恢复与注销清理需有测试。不得读其它插件/浏览器秘密文件验证能力。

### 3.2 高敏操作的授权通信

扫码开始、取消、注销与二维码资源不是普通公开元数据。核实宿主真正的用户授权、会话绑定与CSRF/同源机制；不能把现有只读余额路由或localhost/Origin检查当作充分授权。

优先已认证的Host/Client通信。若不能提供安全契约，不裸开HTTP认证路由。二维码也属于临时登录能力资源，只在授权本地UI短时显示；不把二维码、带票据URL、原始回调或令牌发进模型聊天/图片附件/日志。模型只接收脱敏状态或布尔验收结果。

## 5. 四个独立真实验收关口

1. **扫码**：官方二维码可用，用户在官方支持的设备/方式确认，Host取得实际需要且可恢复的账号态（仅报字段是否存在）。
2. **余额**：该平台会话成功调用真实`/api/v1/balance`，用户在本机对照官网总额/现金/赠送/币种；模型只记一致性结果，不索取凭据。
3. **跨重启**：关闭并重新启动Host/测试进程，仅从安全存储恢复，重新验证余额成功；有文件不等于连接有效。
4. **续期**：不撤销或注销真实用户账号，非破坏性证明短期平台票不可用但长期票有效时可换票，余额最多重试一次后恢复。

扫码成功不等于余额成功，余额成功不等于可续期，持久化存在不等于可恢复。真实联网和账号动作必须先获用户单独同意；未测试的项只标未测。

## 6. 实现约束

- HTTPS/精确官方域与必要路径/端口白名单，按每跳响应来源吸收Cookie并校验跳转；不能默认整段Cookie跨域重放。
- 正确处理host-only、Domain、Path、Secure、HttpOnly、Max-Age/Expires、删除和同名Cookie。账号域票不能发到开放平台域；不编造7天/30天有效期。`Set-Cookie`不能按逗号粗拆。
- MiMo专属HTTP需要看到响应头及Set-Cookie，不能只照搬当前只返回JSON的通用curlJson接口。自动模式如需接管余额HTTP以处理续发Cookie，仍复用已有余额解析与wire；不改全渠道传输和轮询。
- 401/403或已确认的业务鉴权失败至多触发一次续期/余额重试；网络/5xx/429与账号失效分开，有限退避；MFA/验证码/账号票被拒即转需重新扫码。
- single-flight仅限MiMo认证内部；单消费者取消不能误杀其他合法消费者，停用/卸载/注销则必须终止所属任务。
- 每次扫码/注销/切账号推进认证代次。迟到扫码、换票、存储写入和余额回执不得覆盖新状态，尤其注销后不能被旧任务重新写回令牌。
- UI区分扫码完成、余额验证成功、续期能力可用与需重新扫码；先验证再显示已连接。旧手动Cookie单独标模式，不宣传自动续期。
- 扫码/注销是显式认证操作，其即时效果应与设置页草稿保存/放弃明确区分；不得顺手保存其它未保存阈值/关注草稿，也不靠写回`mimoCookie`传播每次换票。
- 修改仅MiMo卡：扫码/重新扫码、取消、状态、注销；手动Cookie保留高级兼容入口，不把二维码放rail胶囊或盖宿主通知。单台手机不能假定可以自扫，另一屏显示或保留手工模式。

## 9. WorkBuddy来源ID诊断（配置已解决，方案留作备选）

### 9.1 现象与根因

用户移动端截图中的模型提供商标识是`workbuddy-api`（显示名为WorkBuddy API）；插件错误却明确在找`workbuddy`。不把截图中的私有网关地址或任何凭据写入此文，也不为本次分析访问该网关。

核对当前v0.9.0源码：

- [WorkBuddy模块](../plans/workbuddy.js#L369)把`GATEWAY_PROVIDER`固定为`workbuddy`；[解析调用](../plans/workbuddy.js#L538-L560)不读取可选来源字段，而是始终把该常量传给模型来源解析器。
- [来源目录校验](../plans/custom-balance.js#L848-L855)按`entry.provider`精确匹配。目录只有`workbuddy-api`时，查`workbuddy`就会返回与截图相同的错误；显示名称不参与匹配。
- 该错误发生在来源查找阶段，早于凭据解析及任何网关HTTP请求，因此不能据此归因Key失效、Tailscale不可达、`/status`错误或OpenAI Responses协议。
- [路径处理](../plans/workbuddy.js#L602-L604)原本已取origin根下`/status`，不是`/v1/status`。不应为了此错误要求用户删掉模型调用需要的`/v1`或改模型协议。

离线对照已用真实发布模块和合成宿主目录/配置完成，未改产品代码：

| 合成条件 | 结果 |
|---|---|
| 提供商ID=`workbuddy`，显示名任意，base带`/v1` | 得到合成积分，首个模拟请求路径为`/status` |
| 提供商ID=`workbuddy-api`，显示名WorkBuddy API | 复现完全相同的未登记错误；凭据读取0、实际/模拟网关请求0 |
| 提供商ID仍`workbuddy-api`，只把显示名改成workbuddy | 仍报同一错误；仅改显示名无效 |

3组对照均PASS。对照的成功响应与凭据均为假数据，不代表用户手机网络、证书、Bearer权限或实际`/status`可达性已经验证。
