## 2. W1 / P1：没有见过的旧配置wire仍被接受

### 位置与原因

[wireMatchesCurrentConfig](../client.js#L1132-L1148)仅在“known存在且known.gen等于本次gen”时检查签名/脏代次；`known`不存在或本次gen不等于最后一次gen就直接绑定当前签名并接受。

[applyResult](../client.js#L1310-L1314)接着给整批响应打上**当前客户端配置**的applied身份。这并不能证明Host已读取相同配置，属于把请求发起时的意图当成数据来源证明。

### 已执行的复现

1. 表单为A配置（a.example、USD），初始请求已发出但尚未返回成功，因此没有known.gen。
2. 保存B配置（b.example、CNY），cleanup使第一个请求失效并启动第二次请求。
3. 第二次请求命中Host旧配置缓存，返回A的wire（A、USD、91.23、gen-original-A）。
4. 实际显示：

```text
UNSEEN_CACHED_OLD_WIRE {"calls":2,"text":"A$ 91.23"}
```

这与当前B配置不符。补测使用真实Badge、真实form快照变化及延迟Promise，无真实外部账户。旧在途请求能abort，并不能防止**新请求仍读到旧Host配置**。

### 修复与验收要求

- 建立可从响应直接验证的配置身份/修订证明，不能依赖“浏览器是否见过这个gen”。
- 可使用Host实际读取配置后产生的公开字段摘要，加上覆盖secret写入的可信配置修订/条目版本；Key指纹负责实际账户身份，配置修订负责保存后的生效确认，两者分工明确。
- 不能让Host仅原样echo请求中客户端给的nonce，同时仍使用旧cfg取数；那不构成生效证明。
- 未能确认来源一致时不展示该条余额，后续重试必须能在Host真实读取新配置后恢复。
- 测试：无历史成功值、首个响应被取消后命中旧缓存；组件重新挂载；快速多次修改；未知gen与历史gen回放；等待Host新配置生效后恢复。

## 3. W2 / P2：重复保存同一Key后永久拒收有效余额

### 位置与原因

[保存把所有secretOps目标标脏](../client.js#L3083-L3091)，即使新输入值与已保存Key相同；这是正常且无法从secret投影事先辨认的操作。

[wireMatchesCurrentConfig](../client.js#L1141-L1147)在`dirty > known.epoch`且gen相同时永远返回false，拒绝路径又不会推进已确认状态。同一Key、相同配置的Host合法响应gen当然不变，所以渠道没有恢复路径。

### 已执行的复现

- 成功显示A的`$91.23`。
- 触发设置页secret写入成功所用的同一失效入口`invalidateCustomChannel(id)`，模拟用户重新填写并保存同一把Key。
- Host连续返回当前有效的同一gen成功结果；连续强刷3次仍为：

```text
KEY_SAME_SEED A$ 91.23
KEY_SAME_AFTER_VALID_REFRESHES —
```

这不是“旧余额暂不显示”的保守行为，而是即使Host已读取当前有效配置也一直拒绝。现有V2 Key测试总是假设Key改变、gen必变，没有覆盖幂等写入。

### 修复与验收要求

- 将“等待保存生效确认”与“实际凭据值是否改变”区分，收到可信的当前修订结果后允许相同gen恢复。
- 不得直接删除dirty检查来修复，否则会重新引入保存后旧配置余额回填。
- 测试必须包括重复输入相同Key、清除本就为空的显式Key并仍使用同一个有效引用、真正Key轮换、Host旧缓存期间的结果拒绝以及当前修订确认后的恢复。
- 建议与W1使用同一套配置修订/数据身份机制，不继续叠加gen黑名单。

## 4. W3 / P2：修改A会丢掉未修改B的回退基线与失败计数

### 位置与原因

[effect每次重建lastList=null/failStreaks={}](../client.js#L1109-L1116)，effect依赖仍包含整个customSignature/configEpoch。现有组件级ref保留的只是applied身份与knownGens，并没有保留各渠道最后成功值与连续失败次数。

[暂时失败回退](../client.js#L1228-L1236)因此找不到B的prev，首次失败就报获取失败。原报告与整改目标明确要求不牵连无关渠道。

### 已执行的复现

1. A与B均成功：A11.11、B22.22。
2. 只改A的URL/确认目标；B配置完全不动。
3. 下一轮返回A的新余额33.33，B仅暂时500（同一gen，transient:true）。

实际：

```text
BASELINE A$ 11.11B$ 22.22
AFTER_EDIT_A_WITH_ONE_TRANSIENT_FAILURE_ON_B A$ 33.33B获取失败
```

正确行为应为A新值，B22.22灰化且累计一次失败，而非立即报错。整体请求失败路径也因lastList为空而连带丢掉其他渠道；内置渠道同样受effect重建影响。

### 修复与验收要求

- 按渠道id与可信身份保留成功基线及失败计数，只有身份确实变化、停用、删除的条目失效；fetch effect重启不等于清空全表。
- 保留普通强刷作废旧请求、轮询防卡死等原行为。
- 测试A改配置/B暂时失败、A只改Key/B暂时失败、已有内置渠道成功后编辑自定义、整体网络失败以及第7/8次失败边界；每个用例都检查旧余额/灰色状态/失败计数/恢复。
