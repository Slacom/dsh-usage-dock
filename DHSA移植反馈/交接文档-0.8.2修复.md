## 1. 现象

`GET /api/plan-usage` 返回：

```json
{ "id": "workbuddy", "name": "WorkBuddy",
  "error": "exec",
  "message": "WorkBuddy 状态读取失败（fetch failed）" }
```

`error:'exec'` + `fetch failed` 是**传输层**失败，不是业务错误。在 `plans/workbuddy.js` 里只有
`fetchStatus()` 的 `fetch()` 本身抛异常（返回 `{ err }`）才会归到 `transportError → error:'exec'`，
即「HTTP 请求根本没拿到响应」。

## 2. 关键事实：响应被服务端 **reset**

WorkBuddy 渠道请求两个回环端点（Node `fetch` 默认发 `accept-encoding: gzip, deflate`）：

| 端点 | 响应体 | 结果 |
|---|---|---|
| `/plugins/dsh-workbuddy-connect/status`（国内版） | 3594 B | ✅ 200 |
| `/plugins/dsh-workbuddy-connect/ai/status`（国际版） | **52 B** | ❌ 连接被重置，**0 字节** |

原始 socket 抓包——失败时服务端**一个字节都没回**（连状态行都没有）：

```
### /ai/status   Accept-Encoding: gzip
    END | 0B |
### /ai/status   Accept-Encoding: identity
    END | 202B | HTTP/1.1 200 OK ... Content-Length: 52 ...
```

`curl` 同样干净复现：`curl --compressed` → `curl: (52) Empty reply from server`；
不带压缩 → 正常返回 JSON。

**判别条件：客户端声明支持 gzip + 响应体 < 1024 B + 带显式 `Content-Length` → 连接必被 reset。**

### 受影响的端点全景（实测）

| 端点 | 响应体 | identity | gzip | 状态 |
|---|---|---|---|---|
| `/plugins/dsh-workbuddy-connect/status` | 3594 B | ✅ | ✅ | 正常 |
| `/plugins/dsh-workbuddy-connect/ai/status` | 52 B | ✅ | ❌ RST | **受影响** |
| `/plugins/dsh-workbuddy-connect/update` | 72 B | ✅ | ❌ RST | **受影响** |
| `/plugins/dsh-workbuddy-connect/probe` | 196 B | ✅ | ❌ RST | **受影响** |
| `/plugins/dsh-workbuddy-connect/ai/probe` | 196 B | ✅ | ❌ RST | **受影响** |
| `/api/plan-usage` | 728 B（**无** `Content-Length`） | ✅ | ✅ | 正常 |
| `/api/version` | 12 B | ✅ | ✅ | 正常 |

⚠️ 注意 `/api/plan-usage` 只有 728 B 却正常，因为它**没设 `Content-Length`**——这正是分水岭。
⚠️ 同时被打坏的是 **WorkBuddy 插件自己的设置卡片与「检查更新」**（`/update`、`/probe`），
不只是 usage-dock 的读数。说明 bug 在宿主侧，不在 usage-dock。

## 3. 根因：两个压缩层互相踩踏

进程内**有两个**中间件都改写了 `res.writeHead / res.end`：

1. **`dsh-web-mobile@3.0.5`** —— `/root/dsha-web-mobile/lib/compress.js`
   加载时改写 `ServerResponse.prototype`，对「完整 JSON 响应」做 br/gzip，阈值 `MIN_JSON_BYTES = 4 KiB`。
   其 `patchedWriteHead()` 会把响应头**延迟提交**（攒着晚一拍写）。
2. **`@deepseek-ai/dsh-host-webserver`** 的 gzip 中间件
   （`compression` 包；`dsh-web-app/cordis.patch.yml:175-177` 配 `compression: gzip` / `compressionThresholdBytes: 1024`）。

### 失败时序（插桩实测，逐行可复现）

```
[WH#1] args=1 sent=false pending=false hdrs=[content-type, content-length, vary]
  -> DEFER (headers held back)          ← web-mobile 攒起响应头，headersSent 仍为 false
[WH#2] args=1 sent=false pending=true
  -> native (guard: sent=true ...)      ← 第二次 writeHead(status) 到来
!! CATCH ERR_HTTP_HEADERS_SENT
-> ERR ECONNRESET
```

1. workbuddy-connect 的 `json$2()`（`lib/index.js:1237-1244`）发响应：`Content-Type: application/json`
   + **显式 `Content-Length: 52`**。
2. 52 B **小于** gzip 阈值 1024 → 中间件判定不压缩（`nocompress('size below threshold')`），
   因此**不设** `Content-Encoding`。
3. 因无 `Content-Encoding`，web-mobile 认为该响应「可延迟」→ 把响应头攒起来，`headersSent` 仍是 `false`。
4. `res.end(payload)` 进入 gzip 中间件的 `res.end` 代理（`compression/index.js:121-126`）：

   ```js
   if (!headersSent(res)) {
     if (!this.getHeader('Content-Length')) length = chunkLength(chunk, encoding)
     this.writeHead(this.statusCode)      // ← 只带 status，再次调用 writeHead
   }
   ```
5. 该重入落到 web-mobile 的 `patchedWriteHead()`（`compress.js:114`）：

   ```js
   function patchedWriteHead(...args) {
       flush(this);                    // ← 先把攒着的头提交掉 → headersSent 变 true
       const raw = typeof args[1] === 'string' ? args[2] : args[1];   // undefined
       ...
       if (!belongs(this) || ... || this.headersSent || ...)          // ← 此刻已是 true
           return origWriteHead.apply(this, args);                    // ← 对已发出的响应再写头
   ```
   `flush()` 是**为副作用**调用的，它自己把 `headersSent` 变成 `true`；紧接着的 guard
   又**因为这个 `true`** 去调原生 `writeHead()` → Node 抛 `ERR_HTTP_HEADERS_SENT`。
6. 异常从 `res.end()` 抛回路由处理函数，被 webServer 兜底 catch 接住
   （`dsh-host-webserver/lib/index.js:248-253`）：

   ```js
   handle(req, res).catch((err) => {
       this.ctx.logger.warn(...);
       if (res.headersSent) { res.destroy(); return; }   // ← 直接销毁 socket
   ```
   客户端收到 **0 字节 + 连接重置**。

### 一句话根因

**`patchedWriteHead` 里「先 `flush`、再判断 `headersSent`」的顺序有缺陷**：`flush` 自己造成的
`headersSent=true`，被同一函数后面的 guard 误判成「别人已经发过头了」。

### 为什么是「一部分」显示错误

国内版其实**完全正常**（实测 `credits.total = 1851`），但 usage-dock 的策略是
「任一已配置版本失败，就不能把另一版本的部分积分伪装成完整合计」：

```js
if (transportError !== null) {
  return Object.assign(planBase(plan), {
    error: 'exec',
    message: 'WorkBuddy 状态读取失败（' + msg + '）',
  })
}
```

于是国际版那条 **52 字节的 `signed-out` 桩响应**把整个渠道一起拖垮，国内版 1800+
积分的真实数据被丢弃 → 胶囊显示「获取失败」。

## 4. ⚠️ 本环境重要限制：内置插件目录受完整性保护

**直接修改 `/root/dsha-web-mobile/lib/compress.js` 无法持久**。

实测证据：

| 时间 | 事件 |
|---|---|
| 07:50:59 | 我写入修复版（sha256 `8f7ce8bc…`） |
| 07:59:55 | **被 App 还原为官方原版**（sha256 回到 `f5902f4f…`） |
| 同时 | 进程代号 `DSHA_WEB_GENERATION` 由 `2` 变为 `3`（App 重启），`repair-builtin.log` 有对应记录 |

关键观察：**同目录只有 `compress.js` 一个文件被重写**，`index.js`/`client.js`/`delete-session.js`
的 mtime 仍是 10-13 原值；我新建的 `.bak` 备份文件也没被动。即存在针对内容的还原，不是整目录覆盖。

结论：

- `/root/dsha-web-mobile` 等 7 个内置插件目录（见 `/root/.dsh/builtin-plugins.json` 与
  `/root/dsha-builtin.txt`）**是 App 托管目录，改动会在启动时被抹掉**。
- `dsh-usage-dock` 是 profile 内的普通 npm 插件（无 `-installed` 标记），**改它能存活**。
- 因此「修宿主 `compress.js`」这条路在本环境**不可作为持久方案**，只能在消费侧绕过，
  或改用户级配置（见 5.3）。

## 5. 修复思路（三条，可组合）

### 5.1 【推荐，你已在计划中】usage-dock 侧声明不压缩 ✅ 已实测有效

在 `plans/workbuddy.js` 的 `fetchStatus()` 里显式声明 `accept-encoding: identity`：

```js
const res = await fetch(base + path, {
  headers: { accept: 'application/json', 'accept-encoding': 'identity' },
  signal: controller.signal,
})
```

原理：声明 identity 后无编码可协商，gzip 中间件不进入上面第 4 步的重入分支，问题消失。

**对线上真实宿主实测（宿主 bug 仍在的情况下）**：

```
现状（仅 accept）：cn 200 3321B signed-in total=1851 | ai FAIL fetch failed (UND_ERR_SOCKET)
加 identity      ：cn 200 3321B signed-in total=1851 | ai 200 52B signed-out   ← 不再 reset
```

整条渠道端到端：`error: exec → 无`，`creditsTotal → 1846`，`accounts → 11 条`。

- ✅ 改动小、语义清晰、只影响本插件的回环读
- ⚠️ **未经重启实测**：本次未验证「改动 usage-dock 后重启 App 是否存活」。它不在
  `builtin-plugins.json` / `dsha-builtin.txt` 清单内、无 `-installed` 标记，且全盘只有
  一份副本，**推断**不会被内置插件还原机制覆盖；但 pnpm 用硬链接管理 node_modules，
  我编辑时把 `workbuddy.js`/`client.js` 的硬链接计数由 2 变成了 1（即写文件时断开了链接）。
  发布/重装依赖时可能被 pnpm 重新落盘覆盖，建议你发布后从 `node_modules` 实机确认一次
- ⚠️ 只修 usage-dock 的读数；**WorkBuddy 插件自身卡片/更新检查仍坏**（宿主 bug 仍在）

### 5.2 【上游根治】修 `compress.js` 的顺序缺陷

建议反馈给 `dsh-web-mobile` 维护者。把 `flush()` 改为可告知「是否本次提交」，并在
**仅 status 形态的重入**时直接返回：

```diff
+    /**
+     * Commit a deferred header set. Returns true when this call is what sent the
+     * headers, so a caller can tell "we just flushed ours" from "nothing to do".
+     */
     function flush(res) {
         const pending = take(res);
-        if (pending !== undefined && !res.destroyed)
+        if (pending === undefined)
+            return false;
+        if (!res.destroyed)
             origWriteHead.apply(res, pending.args);
+        return true;
     }
     function patchedWriteHead(...args) {
-        flush(this);
         const raw = typeof args[1] === 'string' ? args[2] : args[1];
+        // flush() 可能正是我们自己提交了响应头。随后只带 status 的重入
+        // （webServer gzip 中间件在 res.end 代理里的 res.writeHead(this.statusCode)）
+        // 会带着 headersSent=true 走到下面的 guard 并调用原生 writeHead → 抛
+        // ERR_HTTP_HEADERS_SENT → 被 webserver 当成 headersSent 而 res.destroy()。
+        // 已提交的那份响应头更完整，所以这种「只有 status」的重复调用是空操作。
+        // 限定成这一种形态，应用层真正的重复 writeHead 仍会照旧抛错。
+        if (flush(this) && raw === undefined)
+            return this;
```

**验证结果**（独立复刻中间件栈，`verify-standalone.mjs`）：

| 响应体 | `Accept-Encoding` | 修复前 | 修复后 |
|---|---|---|---|
| 52 B (<1KiB) | gzip, deflate | ❌ ECONNRESET | ✅ 200 |
| 200 B (<1KiB) | gzip, deflate | ❌ ECONNRESET | ✅ 200 |
| 900 B (<1KiB) | gzip, deflate | ❌ ECONNRESET | ✅ 200 |
| 3594 B (>1KiB) | gzip, deflate | ✅ 200 | ✅ 200 |

副作用检查：≥4 KiB 自压缩仍工作；应用层真正重复 `writeHead` 仍原样抛错。
完整补丁见 `compress.js.patch`（本目录）。

### 5.4 建议顺带做的健壮性改进（0.8.2）

即你提到的「一方数据够用」思路。**建议做成「降级」而非「丢弃」**——因为国内版是真实数据
（1800+ 积分），国际版只是 52 B 的 `signed-out` 桩响应；直接丢掉国际版会误伤它的用户。

当前逻辑（`plans/workbuddy.js:186-200`）：任一版本失败 → 整体报错。

建议：先看有没有任何版本真的拿到 `credits`：

- **有** → 照常展示该版本合计，并标记 `partial/partialNote`，客户端加一条灰色脚注说明
  「另一版本未取到」，既不丢数据也不把部分值伪装成完整合计；
- **没有** → 保持原有 `api` / `exec` / `signed-out` 分类与文案，行为不变。

#### 5.4.1 Host 侧完整实现（`plans/workbuddy.js`）

**改动 A —— 收集失败原因而非立即判死。** 把 `fetchPlanWithBase()` 里那个
`let transportError = null`、`let semanticError = null` 附近替换为：

```js
  const signedIn = []
  const degraded = []              // ← 新增：记录各版本为何没数据
  let notFound = 0
  let transportError = null
  let semanticError = null
  let semanticLabel = null
  for (let i = 0; i < variants.length; i++) {
    const r = results[i]
    const label = VARIANT_LABELS[variants[i].key]
    if (r.notFound === true) { notFound += 1; continue }
    if (r.err !== undefined) {
      // [0.8.2] 记录而非直接判死：只要另一个版本取到了数据，
      // 就把失败降级为「部分数据」提示（见下方 signedIn 非空的处理）。
      if (transportError === null) transportError = r.err
      degraded.push(label + '：' + (r.err && r.err.message ? r.err.message : String(r.err)))
      continue
    }
    const body = r.body
    if (body === null || typeof body !== 'object') {
      if (transportError === null) transportError = new Error('invalid status response')
      degraded.push(label + '：响应结构无效')
      continue
    }
    if (body.status === 'signed-out') continue // 未登录的版本直接不显示
    if (body.creditsError !== undefined) {
      const detail = typeof body.creditsError === 'string' ? body.creditsError : '积分读取失败'
      if (semanticError === null) { semanticError = detail; semanticLabel = label }
      degraded.push(label + '：' + detail)
      continue
    }
    const credits = creditsOf(body)
    if (credits === null) {
      if (semanticError === null) {
        semanticError = '积分响应结构无法解析'
        semanticLabel = label
      }
      degraded.push(label + '：积分响应结构无法解析')
      continue
    }
    signedIn.push({ label, credits })
  }
```

**改动 B —— 让错误分支给「部分数据」让路。** 把该函数尾部（原 `:186-200` 的三个
`if` 返回块）整体替换为：

```js
  // [0.8.2] 失败降级策略。
  //
  // 原策略：任一已配置版本失败就直接报错，理由是「不能把另一版本的部分积分
  // 伪装成完整合计」。该顾虑合理，但代价过大——只要另一个版本取不到数（哪怕
  // 它压根没登录或本就没有部署），已登录版本的真实积分也会被一并丢弃。
  //
  // 新策略：先看有没有任何一个版本真的拿到了 credits。
  //   - 有 → 照常展示该版本的合计，并标记 partial/partialNote，由客户端在面板
  //          里以灰色脚注说明「另一版本未取到」，不把部分值伪装成完整合计；
  //   - 没有 → 保持原有语义错误 / 传输错误 / 未登录的分类与文案，行为不变。
  // signed-out / 404 依旧不算失败（它们不是「另一方坏了」，只是没登录/没装）。
  if (signedIn.length === 0) {
    if (semanticError !== null) {
      return Object.assign(planBase(plan), {
        error: 'api',
        message: semanticLabel + '：' + semanticError,
      })
    }
    if (transportError !== null) {
      const msg = transportError && transportError.message ? transportError.message : String(transportError)
      return Object.assign(planBase(plan), {
        error: 'exec',
        message: 'WorkBuddy 状态读取失败（' + msg + '）',
      })
    }
    return Object.assign(planBase(plan), {
      error: 'signed-out',
      message: '未登录 WorkBuddy：请安装并登录 WorkBuddy / WorkBuddy AI 桌面应用（dsh-workbuddy-connect）',
    })
  }

  // 主行 = 各已登录版本的合计；unlimited 仅当所有已登录版本都不限额。
  const accounts = []
  const variantsOut = []
  let total = 0
  const unlimited = signedIn.length > 0 && signedIn.every((row) => row.credits.unlimited === true)
  for (const row of signedIn) {
    variantsOut.push({
      label: row.label,
      total: row.credits.unlimited ? null : row.credits.total,
      unlimited: row.credits.unlimited === true,
    })
    if (row.credits.unlimited === true) continue
    total += row.credits.total
    for (const account of row.credits.accounts) {
      accounts.push(Object.assign({ variant: row.label }, account))
    }
  }
  const partial = degraded.length > 0
  return Object.assign(planBase(plan), {
    creditsTotal: unlimited ? null : total,
    creditsUnlimited: unlimited,
    creditsAccounts: accounts,
    variants: variantsOut,
    isAvailable: true,
    // 部分取数：客户端据此加一条灰色脚注，避免把部分合计误读为完整合计。
    ...partial ? { partial: true, partialNote: '以下版本未取到数据：' + degraded.join('；') } : {},
  })
}
```

> 注意 `notFound === variants.length` 的 `not-installed` 分支要**保留在改动 B 之前**，
> 它优先级最高（两个端点都 404 = 插件没装）。
